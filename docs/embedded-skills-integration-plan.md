## 第一阶段实现：云端工程分析＋受控修改＋变更报告

不是只加统计埋点，而是在模型调用循环加入执行指导和结果记录：

```text
网页任务 → Gateway → Runner
  → thread/start 或 thread/resume 注入版本化工程规则
  → 模型读工程 → 提出修改范围 → 调用工具
                       ↑ 网页审批 → 工具结果回给模型 ↺
  → 模型总结分析/修改/验证 → Runner 附执行证据报告 → 网页展示与下载
```

- 平台自有包：`runner/skills/cloud-project-workflow/SKILL.md`。参考附件的分析、修改边界与报告思路重新整理，未复制第三方技能脚本；不依赖作者或开发 Mac 的绝对路径。
- `runner/project-workflow.ts` 管理包 ID、版本 `1.0.0`、SHA-256 和有界证据摘要。生产构建将正文内嵌到 Runner bundle，不需另外挂载技能目录；源码开发从仓库根目录启动。
- `runner/codex-stdio.ts` 在新建和恢复会话时通过 `developerInstructions` 注入规则。已核对本机 Codex 0.149.1 生成的两种请求协议；保留原始用户输入、基础模型指令、只读 sandbox 和 on-request 审批。关闭开关并恢复会话时清除之前的工作流覆盖指令。
- `RUNNER_ENGINEERING_WORKFLOW=true` 显式开启，默认关闭。只应在目标云端 Runner 开启；不会因本地开发而启用现场 USB Runner。第一版是一个短小的条件式工作流，不是 49 个技能全量注册/动态选择器。
- `task.started.data.workflow` 记录版本和哈希，已有工具/审批事件继续流转。完成、失败和中断事件的 `data.workflowReport` 记录命令退出码、文件修改事件状态、审批决策与总耗时，经现有脱敏流程处理；每类最多 100 条、报告总长度限制 64,000 字符。沿用 v1 事件类型与数据库事件持久化，不需新增 Gateway 协议或迁移。
- 工作台显示“已加载”，终态报告默认折叠，可下载 Markdown，刷新后随历史事件恢复。报告存在平台事件中，不自动往用户工程写文件。

### 明确边界

规则引导模型完成阶段，不是硬编码状态机；没有证据时不会标记“分析完成”或“验证通过”。普通问答不要求工程操作，纯分析不授予修改权。修改的硬边界仍是现有沙箱和审批，尚无逐文件 allowlist 强制执行器。

模型最终回复负责工程结论、修改目的和风险；Runner 报告仅汇总观察到的执行证据。shell/MCP 的写文件可能没有 fileChange 事件，因此“没有文件事件”不等于“没有改文件”，报告不能代替 diff 审阅。工具退出 0 不代表硬件验证。拒绝、未知状态、缺退出码均不会升级成成功。

尚未实现通用技能商店、跨 Runner 自动交接、烧录、阶段恢复或完整文件系统审计。此次接入也不修复上游模型超时。

## 产品流程

用户继续在一个 Agent 项目里对话。平台按任务选择少量技能，并在网页显示当前阶段、采用的技能、执行节点、待确认动作和验证结果。

```text
理解需求 → 读取项目事实/约束 → 选技能与执行节点
→ 生成最小修改 → 构建验证 → 确认设备部署
→ 读取运行日志 → 判断验收标准 → 更新项目文档
```

每一步有输入、输出与完成证据。编译成功不等于烧录成功；烧录成功也不等于产品功能正常。

## 技术落点

### 1. 技能目录与选择

增加平台维护的技能注册表，记录 ID、版本/内容哈希、适用目标、依赖工具、节点能力要求、输入输出和风险。首版每轮只选择 1–3 个相关技能；不要把 49 份正文全部塞入上下文。

只从管理员审核的目录解析技能路径。用户可以表达想用哪个技能，但不能直接提交服务器绝对路径、任意脚本或提权配置。

### 2. Runner 读取技能

将获准使用的技能制作成独立版本包，保留必要 references/scripts/assets，相对链接随包校验。发布时只读挂载到云端沙箱可见位置，并在任务开始时提供所选技能入口、规则来源、允许修改范围及验收目标。

首版可使用明确的任务上下文和只读文件读取，不依赖未经验证的 Codex 自动发现行为。若接入 CLI 原生技能输入，先按固定的 0.149.1 协议生成完整类型并验证加载与会话恢复，不猜 API 字段。技能切换、失败和产物写入事件均应出现在平台运行记录中。

技能描述是执行指导，不能自行授予权限。真正的写文件、命令和设备限制由平台/执行器实现。不要让技能覆盖主机权限、平台审批或其他租户隔离。

### 3. 项目文档位置

共享技能属于平台的只读版本包；每个项目自己的资料和结果属于该项目 workspace，建议使用：

```text
docs/project-profile.md         项目型号、SDK、命令及来源
docs/hardware/PINMAP.md         项目唯一引脚表
docs/hardware/PITFALLS.md       通用问题与已验证限制
docs/hardware/peripherals/     按实际使用的外设建文档
docs/verification/             构建、部署、运行证据
docs/changes/                  每次修改摘要
```

已有项目文档以当前权威位置为准，不制造重复台账。项目知识导入遵循 `team-cloud-delivery.md`，不能把原始附件整包放进生产 release 或 Runner 会话状态目录。

### 4. 云端与现场交接

先落地云端的工程分析、需求拆解与修改；设备阶段另加受控动作，不把整个云端模型会话和 Key 搬到现场电脑。

跨节点交接绑定项目、任务、代码版本和产物哈希，验证归属、大小与目标路径后传输；设备报告也带相同标识。禁止双方依赖同名目录自行同步，否则容易部署旧产物。

泰山派的确切板型、系统、基础工程和 USB 模式未确认。需先区分“向既有系统部署 APP”与“刷写整机固件”：前者不应默认走全盘烧录。若实际为 Linux 板卡，需要适配其已验证的交叉编译与 APP 部署命令，不能套用 ESP-IDF、Keil 或 MCU OpenOCD 流程。ADB、USB 网络等只作为待确认候选，不宣称已经可用。

### 5. 审批与资源

保留现有网页审批队列，并让设备审批明确显示节点、目标设备、动作、代码/产物哈希和恢复方式。审批绑定这一次动作，不允许一个“运行 workflow.py”许可隐含授权后续所有设备写入。

每块设备设置互斥锁；阶段有超时与取消，失败不继续烧录。先保持每节点并发 1，小任务按需加载资料；日志分批传输并限制体积，不为每个 skill 启动一个常驻 Agent。现有 Runner 忙时会拒绝任务，持久队列与跨阶段恢复仍需实现。

## 建议实施顺序与验收

1. 云端技能 MVP：注册表、只读包、按任务加载、界面显示所用技能/版本。用一个已有工程验证能读真实文件、遵守修改范围、生成可审阅结果；缺文件时指出缺口。
2. 现场设备 MVP：确定一块泰山派、已通过的 APP 部署命令、设备识别和运行成功判据。先验证手动命令闭环，再接平台审批与日志。
3. 跨节点自动流程：版本化交接、设备锁、幂等任务和失败恢复。验收拒绝审批、USB 拔出、重复任务、过期产物、跨项目访问均不会错误执行。
4. 稳定性单独验收：分别统计直接方案请求、Agent 多轮及工具任务的成功率、耗时与错误。可先以同一配置 10 次方案请求和 3 组多轮工具任务作为样本，不用“Runner 在线”替代结果。

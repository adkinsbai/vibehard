# 原生模块到 PCB 自动布线的本地验收

基线：`9fc6ec5`，开发分支 `codex/eda-native-module-chain`。本报告记录 2026-09-28 在本地 checkout 上完成的验证；未据此声称线上版本已经更新或硬件电路已通过审核。

## 样板与接入方式

团队正式模块尚未交付，因此新增 `lib/eda/modules/sample-led/` 作为**软件链路测试样板**。它包含 KiCad 原生单页原理图、PCB 设计块、工程文件、库表和 `manifest.json`。清单固定模块 ID/版本、每个原生文件的 SHA-256、VCC/GND 端口的方向、电压范围和实际引脚位置。结构校验会拒绝未声明文件、路径穿越、哈希不符、缺失或位置错误的端口；KiCad CLI 导出的真实网表再确认端口所在网络。该样板的电阻、LED、封装和供电范围**没有经过硬件工程审核**。

Agent 的受控命令增加 `insertModule`：按版本插入模块内部器件、网络和 PCB 设计块内已有的走线，仅向外暴露清单声明的端口。模块内部器件、网络和走线不可由后续受控命令任意改写；必需端口未连接时，页面不允许生成原生工程。生成的 KiCad 原理图携带来源属性，保存并读回时可以恢复模块实例和其内部走线。Agent 仍须提交可审阅的修改，用户接受后才进入草稿。

本轮起，正式 Agent 目录改为只读取数据库中经独立审核发布的版本；样板不会自动出现在正式目录。代码已加入受控原生包入库、审核和版本目录，但没有真正经过硬件审核并发布的模块，也未在生产数据库应用迁移。现有模块在生成工程时展开为单页器件与网络，暂非多页层级子图。保存后从原理图读回可恢复模块来源，但从已保存 PCB 读取人工改动并合并回下一次 Agent 草稿尚未完成。

## 可复核的真实工具链结果

- KiCad CLI `9.0.8` 导出样板网表，VCC/GND 与清单端口相符；样板原理图和 PCB 能读入现有 EDA 文档模型。
- 插入模块、添加两针电源接口并连接端口后，生成原生 `.kicad_sch`、`.kicad_pcb`、`.kicad_pro`。候选为 3 器件、3 网络；原始空工程保持不变。候选原理图再经 KiCad 导出网表并由平台读回，模块 ID 和锁定的内部成员可恢复。
- 手动参考布线候选的 KiCad ERC **0 项**、含原理图一致性检查的 DRC **0 项**。这是软件样板的规则检查结果，不等于功能、电气裕量或可制造性验证。
- 将同一候选的外部走线清除、保留模块原生 PCB 内部走线后，KiCad 原生 DRC 报 **2 项未布通、0 项原理图不一致**。使用 Freerouting `2.4.1` 可执行 JAR，经 KiCad `pcbnew` 导出 DSN、自动布线、导入 SES 后，新候选的未布通数为 **0**，原理图不一致仍为 **0**，其他 DRC 问题未增加。原板 SHA-256 `9999112aa2038083de48ffb73f8470314c41b4b5de7450f10d6d88696840893a` 在布线期间不变；自动布线候选 SHA-256 为 `fcdd7ad7333282e2e31f73119ae96af68c43afa9fb7af6f457253bba315a89aa`。
- 测试 JAR 下载自 Maven Central 的 Freerouting 2.4.1 发布包，校验 SHA-256 `fb2e91df901fa50cd23a09ab42793af0ece4f3b1f3857d6724dd6f9c0c00be98`；JAR 不进入仓库。适配器要求部署方固定完整 SHA-256，且只返回独立候选，不直接覆盖用户工程。

本地完整证据位于被 Git 忽略的 `.eda-data/module-chain-verification/`：`result.json`、`freerouting-result.json`、原生工程、KiCad ERC/DRC 报告、DSN、SES 和自动布线候选 PCB。可先运行 `pnpm exec tsx scripts/verify-eda-module-chain.ts` 复查模块/原生文件；自动布线需在装有 KiCad 9 的 Linux 上配置 `FREEROUTING_JAR`、`FREEROUTING_JAR_SHA256` 后运行 `scripts/verify-eda-module-freerouting.ts`。

- 当前开发分支**未发布到 `ldcx.tech`**，本轮没有新功能的登录浏览器验收、真实模型对话评测、多人负载测试、服务器部署、生产数据库/OSS 写入或硬件打样。

下一阶段必须先完成首个模块的独立硬件审核，并构建云端镜像；随后用真实设计模型连续测试“理解需求 → 选择模块 → 接端口 → 修改原理图 → 原生保存读回 → PCB 自动布线”，并在公网按账号隔离验收。PDF 与立创 EDA 的可靠导入仍是独立工作，不能由此样板结果推断已跑通。

## 2026-09-28 补充：云端 worker 候选实现的隔离验证

上述“云端 manager/worker 尚未接入”的描述是本轮开始时的状态。当前分支现已增加 `routeStart`、`routeStatus`、`routeCandidate` 控制动作和独立的 worker 布线任务。任务只读取已保存的原生工程，在该工程外的私有任务目录保存快照、DSN/SES、检查报告与候选；`routeCandidate` 返回前复核原理图、PCB 及随任务复制的工程文件哈希，若源工程变化则返回 409。候选不会直接覆盖当前 KiCad 工程。镜像构建定义固定下载 Freerouting 2.4.1 并校验上述完整 SHA-256，任务执行时不下载代码；Java 进程限制为 512 MiB、单核和 300 秒，输出、输入与候选大小均有限制。还未实际构建或发布这个镜像。

在 WSL Ubuntu 26.04 使用 KiCad/pcbnew 9.0.8、Java 25 和校验后的同一 Freerouting JAR，运行 `services/eda-desktop/verify_routing.py` 对隔离复制的原生样板实际执行 worker 任务：状态到达 `ready`，原生 DRC 的未布通 **2→0**、原理图一致性 **0→0**、其他违反项均为 **0**；源 PCB SHA-256 始终为 `9999112aa2038083de48ffb73f8470314c41b4b5de7450f10d6d88696840893a`。候选生成含随机 UUID，每次字节哈希不同。`python3 -m unittest test_routing.py test_server.py test_manager.py` **26 项通过**，涵盖 manager token、跨 owner/jobId、重复任务拒绝、源原理图或 PCB 变化 409、中断后状态、保留任务累计空间及 DRC 报告结构校验。worker 当前限制每任务 32 MB、最多保留 3 项、所有持久数据 256 MB、单个 DSN/SES 等工具输出文件 8 MB，且启动与中间阶段检查磁盘余量；这是代码约束，不代替容器空间压力测试。`/usr/bin/time -v` 对一次**没有图形桌面**的独立测试报告最大 RSS 281856 KiB、耗时约 12.7 秒；这个数不代表与 KiCad GUI 并行时的容器总峰值，也不是三账号容量测量。正式 manager 当前对每 worker 限制约 1280 MiB、全局最多 3 个桌面；该限制下的真实容器运行、三账号公网、断线重启、正式模块硬件审核及生产发布仍待验证，不能把本地 worker 结果表述为线上已可供所有人使用。

后续跨层审查将 `ready` 门槛收紧为**全部未布通归零**，部分改善（例如 100→99）只返回失败，并保留前后计数；同时候选保留 `.kicad_pro`、符号/封装库表及固定名 `.kicad_dru` 的原始文本，接受时以 `verifySources:true` 检查目标工程是否与候选字节一致。自定义工程内其他原生文件、工程本地或外部库表 URI 被保守拒绝，避免候选丢配置。当前网页候选交付受限于每份原理图/PCB 900 KB、每份辅助文件 128 KB、编码后启动请求约 1.9 MB；此前桌面允许的更大工程不一定能布线，超过限制时会明确拒绝。新增私有 `/v1/modules/verify` 原生网表接口，manager 使用短生命周期、无项目挂载、无网络的 KiCad 容器校验输入；WSL 真实 KiCad 测试样板通过。Ubuntu 26.04 本机仓库 `kicad` 为 9.0.8，但**尚未构建生产 Docker 镜像**，镜像实际版本、隔离资源及公网能力仍未验证。当前 Python 相关测试 **35 项通过**，真实 worker 布线再次得到 2→0。

进一步对同一真实布线结果执行“获取候选 → 以 `verifySources:true` 初始化同 owner 的新工程 → 再次校验相同候选”，提供的原理图、PCB、工程配置和库表字节均保持一致；源工程 PCB 未变。发现并修复了候选初始化自动补充默认库表导致二次校验 409 的问题。对中断后只残留部分文件的新目标工程，写入前逐项比对预存原生文件；旧文件与候选不符时 409 且不写入新板，匹配时可续写，并在完成后再次核对。此回归加入后 Python **36 项通过**，实际 worker 布线/另存再次通过。私有模块校验响应和桌面启动响应会返回 KiCad 版本，仅支持主版本 9；WSL Ubuntu 26.04 的 apt 候选和本机安装均为 9.0.8，但这不能替代对实际 Docker 镜像及生产发布包的验证。

## 线上旧版本的即时检查（与本分支分开）

2026-09-28 在已登录的 `https://ldcx.tech/vibehard/app/eda` 页面，现网显示设计模型已接入，但从空白草稿提交“5V 输入、R1=1kΩ、D1 LED、+5V → R1 → D1 → GND，并说明 LED 正向压降和电阻功耗核对”后，页面立即显示“工程数据或请求格式不正确”，没有生成修改提案。因此**现网这项基础 Agent 任务失败**。跨层审查定位到前端在尚未打开工程时仍发送 `projectId: ""`，而 Agent API 只接受缺省值或有效 UUID；请求在模型调用前被拒绝。本分支已修复为空 ID 时省略字段，并以先失败后通过的回归测试复核。该修复尚未部署，不能当作线上已恢复。现网版本也未包含本分支的模块审核和云布线代码。正式放行仍需首个硬件审核模块、云镜像和生产数据库迁移、真实模型连续任务、至少两账号的公网隔离及布线/候选接受验收。

同一线上会话选择已有 `Agent三轮验收-20260926` 工程并只读加载已保存原理图后，草稿显示 5 个器件、4 个网络，R1 与 R2 均为 1kΩ。提出“只将 R1 改为 2kΩ，其他器件、网络、PCB 走线不变”后，线上 `deepseek-v4-pro` 实际返回一项 `setComponent` 提案；页面候选仍为 5 器件、4 网络，R1=2kΩ、R2=1kΩ，并提醒核对电流与电阻功耗。此结果只证实**有效工程上下文下的一次真实模型局部修改提案**；没有应用到原工程，也未做该提案的原生保存、ERC/DRC 或独立多轮重复测试。后续重新读取页面时，待审阅提案已消失、草稿 R1 回到 1kΩ，确认“放弃”生效；没有点击“加入设计草稿”或创建工程。继续尝试清空草稿做独立生成测试时浏览器自动化无法完成确认对话，故不把该任务计为验收通过。
